## 界面与确认行为

公开餐厅场景显式允许`restaurant.service_request`后，当前本人有效就餐组才能收到五类服务建议。卡片显示本组、服务类型与交接边界；按钮在本人勾选“确认将本次服务请求交给店员”之后才能使用。提交创建持久店员服务请求，后续仍由本店员工接收和处理。

勾选绑定当前会话、状态、版本、发问人版本、回复代次和原建议的标识、内容及期限。播放回复等行为改变版本时，旧勾选立即失效；本人必须重新核对当前内容。切换顾客、结束、转人工和场景撤回不能沿用旧勾选。

点击后先读取当前本人接待，核对同一建议及版本，再按原工具合同提交。读取期间发生上下文变化会终止旧读取；已发出的写入由服务端完成判断，前端丢弃不属于当前上下文的迟到结果。不会把旧请求改成新顾客或自动替换成较新的确认版本。

原期限到达后，即使旧的授权读取仍暂存在网络中，卡片也会按实际客户端时间清除勾选并禁用控件，显示“建议已到期，请重新提出本次需求。”服务端继续以实际数据库时钟裁决；浏览器计时器不替代服务端权限和期限校验。401、403或404会清除当前私人接待查询，迟到的旧读取不能恢复操作。

## 使用与启动

现有[主工作台5174](http://127.0.0.1:5174)保持原运行版本和数据库。本次能力在独立development/mock实例验证；按[独立原生启动说明](62-postgres-native-core.md)使用当前构建、runtime120及123迁移建立新的实例，不启动已封存证据根，不替换主库或两类原密钥。

在“场景应用配置”选择同工作空间的公开餐厅场景，明确勾选“允许提出店员服务请求（顾客确认后交接，不执行付款）”，保存后运行文字链路就绪检查。顾客进入本店终端，选择自己的有效就餐组，发送“请加水”等明确需求；在建议卡片核对并勾选确认，再提交。店员从本店“服务与餐后”查看该请求。

会话读取与确认继续使用`GET /api/v1/guest/sessions/:id`及`POST /api/v1/guest/sessions/:id/tools/confirm`。确认正文为原requestId、version、focusVersion及confirmed=true，沿用本人Cookie、CSRF和幂等控制。模拟目标字幕仍使用本店当前授权的餐厅speaker-events路径。
