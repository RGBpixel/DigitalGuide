# 原生餐后评价、独立回访与本人清除后端

沿[餐中服务界面](115-postgres-hospitality-ui.md)继续T20及R-003、R-035、R-047—R-052。本增量完成餐后评价、独立加密回访授权和仅清除凭证的后端检查点。餐后及离店管理页面尚未接通，完整hospitality仍为false；餐中serviceRequests默认能力保持。视频/PPT、直播、发布投放、展厅、企业前台、餐厅、真人形象/声音/语气及全部既有竞品目标保持。

## 实现

- 本人仅在本次就餐实际结束后，按当前就餐版本、发问人、选择范围和明确确认保存评价或回访授权；员工不能代填或代为授权。两者独立，不评价也不影响服务和账单。
- 评价保存期限为30天。回访需单独确认visit_followup用途、联系方式和1—30天期限；服务端依据实际数据库时钟固定本次期限。修改或重新授权是新的明确操作，原键重试不延长期限。
- 回访使用独立用途派生密钥和AES-256-GCM，绑定实例、环境、租户、空间、门店、就餐组、记录、动作、版本、nonce、联系类型及原期限。数据库只保存密文和掩码，接口不返回原联系方式或密文，回访明文不传入SQL。幂等输入使用服务端用途HMAC，不持久保存原联系方式。
- 本人保存后获得仅用于清除对应一项记录的凭证。终端结束或转人工后也可明确撤回；凭证不能读取评价/联系方式、登录、取得员工身份、下单或付款。它放在POST正文中，不进入URL；更新授权后旧凭证失效，同一原凭证重复撤回只保留一次版本推进。
- 撤回清除对应评价正文/评分或可用回访密文/掩码。只保留最少版本、来源、不可变摘要和审计；不在动作、幂等回执或修订中复制正文及密文，不写入记忆、聊天或厨房数据。
- 两API共用数据库中的凭证尝试计数，按来源IP的服务端用途HMAC限制30次/分钟，不保存原IP。失败尝试也计数，不回显凭证；每次仅清除当前凭证对应的一项记录。
- 到期维护使用数据库实际墙上时钟，处理原生来源的记录，不能提前清除或改写原期限。独立worker每秒维护，API读取也检查维护；仅清除凭证入口可在终端已失效时清除本项内容。新动作必须有完整持久结果，半份准备事务、裸写、改期限或改凭证不能提交。
- 本店迎宾/经理可读自愿评价和回访掩码，不能拿到本人清除凭证；厨房、其他租户及其他顾客终端不能读取。

后端接口：

- 本人GET `/api/v1/guest/sessions/:id/dining/parties/:partyId/aftercare`；POST同前缀下的feedback、followup及各自/revoke，须提供当前版本、partyVersion、focusVersion、selectionVersion、CSRF、幂等键和明确确认。
- 员工GET `/api/v1/restaurant/parties/:partyId/aftercare`及`/api/v1/restaurants/:id/aftercare`。员工代客写入明确403，越店或无职责读取拒绝。
- 离店POST `/api/v1/restaurant/aftercare/manage`，正文为本人保存的code及confirmed=true，只返回对应项的清除状态。不得把完整凭证放入日志、URL或共享给其他人员。

本轮使用虚构人物和联系值，未执行真实通知、对外回访、POS、支付、摄像头、识别、发布或推流。这里证明的是可查询在线记录中的逻辑清除，不宣称物理擦除PG的WAL或既有备份；生产保留、恢复后删除与长期运行在T20/G2继续验收。真实形象/声音/语气、目标声源/ASR、现场设备、商户/POS和渠道仍需各自真实接入。
