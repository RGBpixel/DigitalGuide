## 当前能力

`pnpm postgres:recovery` 提供 `backup`、`verify`、`restore`、`inspect`、`unlock`。工具使用私有连接 JSON、独立备份密钥，以及已固定的 PostgreSQL18 Windows 工具集。源需要停止 API、worker 和文件写入进程；工具拒绝存在的业务连接，不主动停止服务。

备份对源业务表取得 SHARE 锁，在同一个导出快照下生成数据库归档，同时复制本地 DATA_DIR，并核对文件清单、内容摘要、表行、序列、迁移、结构和权限。数据库归档、实例文件与原两密钥进入 AES-256-GCM 认证归档，回读验证后独占发布，不覆盖旧备份。同步快照和锁的依据见 [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) 与 [PostgreSQL 显式锁](https://www.postgresql.org/docs/18/explicit-locking.html)。

`verify` 认证整个归档，检查路径、容量和内部文件摘要，并读取数据库归档目录，不连接业务数据库、不执行恢复。因此返回 `databaseRestoreVerified:false`。

`restore` 只接受原绝对 DATA_DIR 的空缺位置和独立空数据库。目标须由原所有者角色拥有，并已有原 API/worker 角色；密码可与源不同，角色 OID 不要求相同，工具不创建全局角色。先关闭业务账号的数据库连接权限，再使用 [pg_restore 单事务恢复](https://www.postgresql.org/docs/18/app-pgrestore.html)，核对全部表行、序列、迁移、结构与权限，然后设置原生控制行 `recovery_quarantined` 并收回业务 schema 权限。

恢复文件保留原资产、空目录与两密钥；`api.json`、`worker.json` 和原生目录标记替换成不可激活的隔离描述，不含可用连接或凭据指针。它们记录原文件摘要。恢复失败保留目标库供核对，不覆盖、合并或自动重试非空目标。

## CHECK 差异的处理

首轮跨集群恢复在摘要检查被拒绝。限定只读诊断证明，492 张表的行与序列完全相同，唯一差异是 16 条 CHECK 约束的嵌套 AND 分组在导出、重新解析后展开。例如 `(A AND B) AND C` 与 `A AND B AND C` 的文本摘要不同。观察到的约束定义与散列保留在证据中；相关 PostgreSQL 解析器代码见 [gram.y](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/parser/gram.y)。

现存原生运行时的原始目录算法保持，归档也保留原始摘要。新增 `check-bool-v1` 补充摘要覆盖同一套完整结构、约束、函数及表/列/函数权限投影，仅合并同类 AND/OR 的结合分组，保留相对次序、常量、比较符、NOT、函数参数、记录/算术分组及引用文本。无法安全解释或过深的表达式拒绝处理。其他约束类型与权限不作放宽。

旧原型归档没有补充摘要时，仍要求原始目录精确相等，不自动转换为新的验证依据。实际数据库检查已证明：改变边界、AND/OR、验证或继承状态、表/列权限、函数执行权限和函数实现，仍被识别为不同。恢复后篡改合成人员行，即使目录摘要相同，也不能通过数据核对；该注入事务随后回滚。

## 启动与运维

现有[本地工作台](http://127.0.0.1:5174)继续运行，无需为本次增量重启。以下命令面向单独准备的原生实例，不能直接用于主工作台的 SQLite 数据目录。

~~~powershell
pnpm postgres:recovery --help
pnpm recovery keygen --key-file '<独立备份密钥文件>'
pnpm postgres:recovery backup --config-file '<原生api.json>' --loader-file '<源库私有运维连接JSON>' --output '<新加密归档>' --key-file '<独立备份密钥文件>' --confirm-stopped
pnpm postgres:recovery verify --archive '<加密归档>' --key-file '<独立备份密钥文件>' --work-dir '<已存在的私有工作目录>'
pnpm postgres:recovery restore --archive '<加密归档>' --loader-file '<独立空目标库连接JSON>' --data-dir '<原绝对DATA_DIR，必须不存在>' --key-file '<独立备份密钥文件>' --confirm-restore
~~~

构建后对应入口为 `node dist/postgres-recovery.mjs`。从匹配代码根目录运行；可用 `--root` 指定兼容迁移目录，`--tools-dir` 指定已经固定的工具集。工具不自动下载安装或启用数据库服务。密码通过受控私有 passfile 传递，清除继承的 PG 连接环境值，TLS verify-full 使用显式 CA；依据见 [libpq 环境变量](https://www.postgresql.org/docs/18/libpq-envars.html)。命令参数、输出和普通日志不得包含密码或密钥值。

`inspect` 可查看数据目录或归档验证锁；`unlock` 需要确认原操作已死亡及准确操作编号，不接管活锁，也不解除恢复隔离。失败库或不完整恢复目录应保留核对，使用新的独立空目标；不能移除标记后直接启动业务。

## 保留的生产要求

当前验证为 Windows PostgreSQL18 与本地 DATA_DIR 的离线工程链路；不是在线对象存储一致备份或大规模生产压测。外部环境密钥、证书/密码文件、模型、AE 等目录和云端资产不自动纳入备份。数据库、源配置与原角色需受信任；恢复 SQL 不是不可信代码沙箱。

原授权、会话、队列和密钥保留为备份事实，不代表备份后发生的撤权、删除、身份变更或过期处理已经应用。必须继续完成撤回/删除传播、身份与会话核对、订单/资金/POS/通知/发布未决回执核对，及受审查的生产启用流程；目前没有激活开关。对象存储、跨目录引用迁移、生产密钥管理与长期运行也继续。

本轮使用虚构身份、合成 PNG 和模拟任务，没有真实克隆、识别、音视频、POS、支付、通知、发布或直播操作。真实服务仍需要已授权账号、设备和现场验收环境；不以此替代真人形象、声音/语气、多轨/模板、多人同屏、批量协作、4K/透明导出、资产迁移、所有接待与发布场景的完整目标。
