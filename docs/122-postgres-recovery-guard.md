# 原生 PostgreSQL 维护与恢复隔离保护

更新：2026-11-25。任务 T20，需求 R-058、R-059，关联 AC-27。本次是恢复前的访问保护，不是原生备份恢复验收。完整平台仍为 134 项需求、38 项任务、65 项验收、26 组能力；27 项本地 verified、T20 in_progress、10 项 pending，G2 与开发目标继续。

## 已实现

程序化 `createApp`、直接 `NativePostgresDatabase.open` 和运行检查工具现在共用原生目录的维护与恢复检查，调用方无需先执行环境配置加载才能获得保护。

- 维护锁存在时，即使锁内容为空或类型不正常，也拒绝打开原生实例。
- 有效、未完成、损坏、目录或悬空联接类型的恢复标记都保持关闭。原生实例不能借用 SQLite 的恢复只读验证模式。
- 已打开的连接池在新事务入口、取得连接并开始事务后、提交前检查保护状态。内层事务遇到隔离错误，即使调用方捕获并移除测试标记，外层仍回滚。
- 既有 API 请求及 worker 领取任务返回明确错误。请求期间拒绝返回 503 和安全中文原因，不泄露私有路径、凭据或数据库原文。
- 正常原生实例的目录、两密钥、配置、cookie 和既有数据库结构保持。

保护分别使用 `PG_RUNTIME_MAINTENANCE`、`PG_RUNTIME_RECOVERY_ISOLATED`。显式给原生 API 设置 `recoveryValidationOnly` 时，已有更早的 `PG_RUNTIME_MODE_INVALID` 检查继续生效。

实现位于 `packages/postgres/src/runtime-config.ts` 和 `runtime-database.ts`。没有新增迁移；PostgreSQL 001—124/runtime121 继续冻结，下一 125；SQLite 052/下一 053 不变。

## 启动与检查

现有工作台仍使用原运行中的 [本地入口](http://127.0.0.1:5174)，不需要为本次检查重启。

新原生验证实例仍按[原生运行文档](62-postgres-native-core.md)创建并显式选择开发/沙箱与 mock。运行配置与密码文件保存在私有位置；正常实例可用以下命令只读核对：

~~~powershell
pnpm postgres:runtime check --config-file '<私有原生实例的api.json>' --role api
~~~

维护或恢复隔离错误应先保留现场、检查原操作。仓库没有提供原生恢复激活开关。证明中移除标记只用于全新普通合成实例的故障注入收尾，不是恢复数据的激活步骤，不应照搬到业务恢复操作。

本轮已成功的 `native-recovery-guard-proof.ts` 生产器及其私有根保持关闭，不重新执行。后续检查使用新的独立实例，不覆盖或重新激活本轮证据。

## 能力边界与后续条件

本次保护是应用访问检查，不能替代数据库与文件的一致性快照、数据库级停写、权限隔离或运维协调。检查之间存在系统调用与数据库提交的时间窗口；不能据此声称已获得在线一致备份、已取消全部在途外部操作，或可抵御有权限直接修改数据库/目录的管理员。

原生 PostgreSQL 加密备份、对象存储一致恢复、恢复后撤权/删除对账、身份和未决任务/资金/通知/发布回执核对、生产激活仍待实现与验收。SQLite 的既有[加密恢复](60-encrypted-recovery.md)边界保持，不代表 PostgreSQL 已支持同样操作。

本轮使用虚构人员、合成数据和 mock；没有真实识别、音视频、克隆、支付、通知、发布、直播或广告操作。真实服务仍需要已授权的供应商账号、硬件及现场素材/验收环境；这些外部条件不阻止继续完成原生备份等独立工程工作。真人形象、声音及语气复刻、多轨和模板、多人同屏、批量协作、4K/透明导出、资产迁移、各类接待、直播和多平台发布等完整平台要求继续保留。
